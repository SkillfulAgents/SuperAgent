# SUP-877 — Managed email service research

Researched 2026-09-21 against first-party product documentation and published pricing. This is a documentation review, not a live API/deliverability test or vendor assurance. No vendors were contacted and no accounts, domains, or paid resources were provisioned.

## Recommendation

Evaluate **AgentMail and Nylas Agent Accounts before committing to the SES/S3/SNS/SQS/Lambda implementation**. Both provide hosted, programmable mailboxes and can remove most of the proposed transport, parsing, storage, and threading work. AgentMail is the closest documented match to our tenant/inbox model and wildcard address requirement. Nylas is a strong full-service alternative with lower published incremental mailbox pricing, but domain provisioning and tenant isolation need clarification.

If retaining our own SES Tenants is a firm requirement, evaluate **CloudMailin receiving + SES sending**. It removes the receiving/MIME/attachment pipeline while leaving our mailbox database and application semantics under our control. Inbound.new is another promising managed transport option, with less documented tenant control in the materials reviewed.

These are alternatives for evaluation, not a decision to replace the agreed product contract. The existing AWS design remains the fallback.

## What must still belong to us

The independently deployed Email Gateway (proposed CF Worker runtime) remains the authenticated agent API regardless of provider. It owns its code, database, storage, provider credentials, and operations; platform supplies identity validation only. SuperAgent calls the gateway directly, without a platform email adapter. Our integration classes, mailbox ownership, four admission modes, current agent ACL checks, sender eligibility within an outbound conversation, policy changes, agent session mapping, claims/acknowledgments, run budgets, and tool approval rules remain application responsibilities. Provider filtering can assist but cannot replace these semantics. SUP-912 remains separate.

No reviewed service documents a native integration that writes our exact service-owned mailbox schema. Hosted providers deliver API resources and webhooks; we still need a small verified ingestion adapter with durable acceptance and reconciliation. We can store provider IDs, mailbox mappings, and durable work events locally while fetching bodies/attachments through the Worker, rather than duplicating every original. Keeping a local full-body mirror is a separate retention/availability decision.

## AgentMail: closest feature match

AgentMail provides API-created inboxes, message history, threads, replies/reply-all, attachments, and parsed reply content. It supports signed webhooks and API retrieval. The model maps naturally to one Pod per platform organization and one inbox per agent; pod- and inbox-scoped keys are documented. [Messages](https://docs.agentmail.to/messages), [FAQ](https://docs.agentmail.to/faq), [multi-tenancy](https://docs.agentmail.to/multi-tenancy), [webhooks](https://docs.agentmail.to/webhooks-overview)

Its domain API explicitly supports `subdomains_enabled`: publish wildcard MX once and create inboxes such as `agent@acme.mail.example.com` without registering each child domain. However, these inboxes use the parent sending identity/DKIM and share that reputation. Separately register each org subdomain to obtain a distinct sending identity; doing so brings domain counts and provisioning back into the cost model. Independent DKIM does not guarantee that all receiving systems or the vendor treat sibling subdomains as independent. [Custom domains](https://docs.agentmail.to/custom-domains), [domain strategy](https://docs.agentmail.to/managing-domains)

Useful overlap with our modes: send, receive, and reply allow/block lists exist at org, Pod, and inbox scope. However, reply filtering branches on `In-Reply-To`, skips the receive list, and allows replies by default when reply lists are empty. This does not establish our stronger requirement that the sender was actually a recipient of the agent's prior outbound message in that conversation. We must enforce that and the internal-only mode ourselves, including replies. [Lists](https://docs.agentmail.to/lists)

Send/reply/forward/draft-send operations support an `Idempotency-Key` header with a documented 24-hour lifetime after send completion. Keep our own durable intent beyond that window. The inbox events endpoint currently documents label-change events; do not assume it is a complete replay feed for received mail. Design reconciliation around message listing and stable IDs, then test missed-webhook recovery. [Idempotency](https://docs.agentmail.to/idempotency), [inbox events](https://docs.agentmail.to/api-reference/inboxes/events/list)

Unresolved: the Pods guarantee is data/resource isolation. Bounce guidance still discusses account-level review. I found no explicit public promise of per-Pod suppression or automatic reputation suspension equivalent to the SES tenant configuration we selected. Confirm this, retention/export, inbound size caps, webhook replay guarantees, and high-inbox/domain pricing. [Pods](https://docs.agentmail.to/documentation/core-concepts/pods), [bounce guidance](https://docs.agentmail.to/knowledge-base/emails-bouncing)

## Nylas: full hosted mailboxes, not just connected accounts

Nylas Agent Accounts create mailboxes without a user's Gmail/Outlook account or OAuth flow. They expose the same Messages, Threads, Drafts, Attachments, and Webhooks APIs as connected accounts, plus calendars. Agent Accounts is documented as generally available. [Quickstart](https://developer.nylas.com/docs/v3/getting-started/agent-accounts/), [GA announcement](https://www.nylas.com/blog/pr/nylas-launches-agent-accounts-giving-ai-agents-their-own-email-address-and-calendar/)

Inbound mail is stored and available through the API, supports polling and webhooks, and is threaded using RFC headers. Outbound supports To/Cc/Bcc, attachments, and reply context. The documented outbound limit is 25 MB total. Inbound attachment limits can cause individual attachments to be dropped while the message is retained; surface that condition instead of implying the email was received intact. [Mailbox behavior](https://developer.nylas.com/docs/v3/agent-accounts/mailboxes/)

Workspaces group agent accounts under reusable policies/rules. Documented controls include retention, size/storage/send limits, and address/domain lists. These are useful primitives, but platform ACLs and recipient-bound reply admission still belong to us. The newer policy/workspace guide describes workspace-scoped outbound rules, while some older overview text still calls them application-scoped; verify actual behavior in the evaluation. [Workspaces](https://developer.nylas.com/docs/v3/agent-accounts/workspaces/), [policies](https://developer.nylas.com/docs/v3/agent-accounts/policies-rules-lists/)

The largest practical question is domain scale: public Pro monthly pricing includes ten custom domains. The domain API guide also says it requires service-account credentials and a contract including domain management, while the quickstart shows dashboard/CLI provisioning. Clarify the supported fully automated flow and enterprise pricing for hundreds/thousands of organization subdomains. No arbitrary wildcard child-domain feature was found in the reviewed guide. [Domain management](https://developer.nylas.com/docs/v3/email/domains/)

Nylas documents abuse restrictions at sender, domain, organization, application, and grant levels. Workspace grouping does not by itself establish SES-equivalent reputation/suppression isolation. Confirm account-suspension impact and scoped credentials as well as idempotent send/reconciliation semantics. [Limits and enforcement](https://developer.nylas.com/docs/v3/agent-accounts/send-limits/)

## CloudMailin: buy ingestion, retain SES Tenants

CloudMailin delivers parsed JSON with SMTP envelope information, bodies, headers, reply text, and attachment references. It supports a wildcard custom domain such as `*.mail.example.com`, explicitly matching one level of customer subdomains. It can put original MIME or parsed JSON into our bucket. This would remove our SES receiving, SNS/SQS ingestion wiring, Lambda parser, and attachment extraction implementation. [Domain matching](https://docs.cloudmailin.com/receiving_email/using-your-own-domain/), [full-message storage](https://docs.cloudmailin.com/receiving_email/store-full-email-in-aws-cloud-storage/), [inbound](https://www.cloudmailin.com/)

Relevant to the earlier R2 question: CloudMailin explicitly documents and says it has tested **attachment uploads to Cloudflare R2** through its S3-compatible storage integration. The reviewed full-message setup guide documents AWS S3/Azure/GCS, so confirm that full original MIME can use the same R2 configuration before promising an all-R2 flow. [R2 attachment support](https://www.cloudmailin.com/blog/receive-email-attachments-in-s3-compatible-storage)

Proposed integration: CloudMailin writes objects, an authenticated endpoint in the standalone Email Gateway commits parsed mailbox records/events, and agents use that gateway API directly. Acknowledge only after durable acceptance. This buys the hard email parsing work but does not provide a complete indexed/threaded mailbox service. Retain SES Tenants for outbound and the chosen tenant controls. A direct callback means the proposed database-only boundary for the agent API can be maintained with a separate ingestion adapter, without a Lambda MIME processor.

## Other options screened

- **Inbound.new:** public docs include email list/get, attachment retrieval, send, reply/reply-all, and delivery retry APIs; parsed webhooks are documented. It advertises unlimited addresses on registered domains. Its domain index describes child domains inheriting parent verification, which is not proof that arbitrary subdomains require no registration or incur no domain charge. No explicit SES-Tenant-equivalent isolation was established in reviewed docs. [API index](https://inbound.new/docs/llms.txt), [webhooks](https://inbound.new/docs/api-reference/webhook), [product](https://inbound.new/)
- **Resend:** supports inbound retrieval and parsed content as well as sending; it is not send-only. Its multi-tenant guide explicitly describes shared account reputation and possible account-wide suspension; separate-account BYOK requires manual account creation. It would remove transport/parsing but leave our mailbox/thread model and isolation concerns. [Receiving](https://resend.com/docs/dashboard/receiving/introduction), [multi-tenancy](https://resend.com/docs/knowledge-base/setting-up-resend-for-multi-tenants)
- **Mailgun:** parsed inbound routing plus outbound, with real subaccounts and per-domain suppression. A credible managed transport option, but inbound route storage is documented as temporary, so it does not remove our persistent mailbox/thread layer. Confirm subaccount availability, suspension scope, and current retention by plan. [Subaccounts](https://help.mailgun.com/hc/en-us/articles/16380043681435-Subaccounts), [suppression scope](https://help.mailgun.com/hc/en-us/articles/360012287493-Suppressions-Bounces-Complaints-Unsubscribes-Allowlists), [route storage](https://www.mailgun.com/blog/product/store-a-temporary-mailbox-for-all-your-incoming-email/)
- **Postmark:** provides inbound JSON parsing, attachments, reply text, and outbound delivery; its retained message records do not by themselves supply our mailbox/session semantics. It is another transport/parser candidate rather than the strongest full-mailbox fit. [Inbound parsing](https://postmarkapp.com/developer/user-guide/inbound/parse-an-email)
- **MailSlurp:** genuine programmable persistent/custom-domain inboxes, sending, attachments, and webhooks, despite its testing focus. Production/external sending begins on paid tiers; the reviewed sources do not establish tenant reputation isolation. Worth a reserve option rather than ruling it out as testing-only. [Programmable email](https://www.mailslurp.com/product/email/), [pricing](https://app.mailslurp.com/pricing/)
- **Postfleet:** offers agent mailboxes and content screening, but its documented send endpoint is plain text, one recipient, no Cc/Bcc or attachments. That conflicts with the proposed email capability, so it is not shortlisted. [Send limitations](https://postfleet.ai/docs/sending)

## Decision gates before choosing a provider

1. Provision two customer domains and multiple agent inboxes automatically; confirm wildcard behavior, separate DKIM options, quota accounting, and commercial terms for embedded mailboxes.
2. Establish the distinction between data isolation, domain reputation, suppression scope, per-tenant throttling, and account-wide suspension. A provider need not offer complete isolation to be useful, but differences from SES Tenants must be explicit.
3. Exercise real replies, reply-all, Bcc, forwarding, forged references, changed Reply-To, HTML-only mail, and attachment truncation with our four modes. Determine which authentication verdicts the provider exposes and what mail it rejects before our code sees it.
4. Verify webhook authentication, retry duration, missed-event reconciliation, retention/export/deletion, provider ID stability, and ambiguous outbound-send handling. Do not infer lossless execution from provider webhooks or code samples.
5. Obtain workload pricing for expected organizations, active inboxes, separately registered subdomains, sent/received volume, storage, bandwidth, support, and SLA. Published entry prices alone do not answer fleet cost.

No production implementation has started. The next decision is whether to evaluate full managed mailboxes (AgentMail/Nylas), managed ingestion while retaining SES (CloudMailin), or keep the AWS fallback after comparing these gaps.
