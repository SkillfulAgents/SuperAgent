- never `db.transaction(` (lint rule `no-db-transaction`, exempt only inside `src/shared/lib/db/`): the app must run on drivers that offer batches, not interactive transactions. A pure multi-statement write is `await batch([...builders])` from `@shared/lib/db/batch`; read-then-decide logic is one conditional statement (`UPDATE … WHERE` with a subquery, `insertWhere()` for `INSERT … SELECT … WHERE`, a compare-and-set) whose change count via `changesOf()` is the decision. Data migrations' `run()` must be idempotent: the ledger row is written after it, not with it
- the database is opened once, explicitly: an entry point `await openDatabase()` before anything else, then `db` / `getDb()` from `@shared/lib/db`. Nothing outside `src/shared/lib/db/drivers/` imports `better-sqlite3` or a drizzle driver; raw SQL goes through `db.run(sql\`…\`)` / `db.get(sql\`…\`)`, and a run result is opaque (`changesOf()`), never `.changes`. Migrations run from `src/shared/lib/db/migrations/bundle.ts`: after `drizzle-kit generate` run `npm run db:bundle` (`npm run db:generate` does both), or `bundle.test.ts` fails. Tests build a database with `createTestDatabase()` from `@shared/lib/db/testing/create-test-database`; a test file whose access is fully awaited goes on `scripts/libsql-must-pass.txt`, which CI runs with `DB_DRIVER=libsql` and which only grows. Every drizzle `.all()` / `.get()` / `.run()` is awaited or returned from an `async` function (lint rule `no-sync-drizzle-terminator`; its allowlist in `eslint-rules/no-sync-drizzle-terminator-allowlist.json` holds exact per-file counts and only shrinks), so a function that touches the database returns a Promise and its callers await it; `@typescript-eslint/no-floating-promises` is on for `src/shared/lib` and `src/api`, so a deliberate fire-and-forget call is written `background(f(), { name: 'component.operation' })` from `@shared/lib/background`, never `void f()` (lint rule `no-floating-work`; `.catch()` handlers stay inside the work): it reports a rejection instead of letting it reach the process handler, which quits Electron, and it is where Workers will hand the work to `waitUntil`. Tests wait for it with `backgroundSettled()`
- settings and the small host records (tenant id, auth secret, host container tokens, …) live in the database's `app_records` table, not in data-dir files: `await getSettings()` reads fresh every time (no process cache — read once per operation and pass values down; never keep settings or anything built from them in module state), and `mutateSettings(mutator)` is a revision compare-and-set whose mutator may run more than once, so it must be synchronous and side-effect free. Identities created once use `getOrCreateRecord()` (insert-if-absent). Read [docs/settings-storage.md](docs/settings-storage.md) before touching `src/shared/lib/app-records/` or `config/settings.ts`
- state that must outlive a request or reach another process (pending flows, rate limits, claims, cache snapshots, live hints) goes through AppState, `appState()` from `@shared/lib/app-state`, not a new module-level Map: declare a typed namespace or topic, use a strong namespace's atomic operations (`insertIfAbsent`, `compareAndSet`, `increment`, `consume`) instead of get-then-set, and keep functions, Promises and sockets local. Entry points `await initializeLocalAppState()` after `openDatabase()`; the shared test setup installs a fresh one before every node-environment test. Read [docs/app-state.md](docs/app-state.md) before adding a namespace, a topic or a backend
- scheduled or recurring background work goes through a `Task` on `taskManager()`, and a background service registers with `serviceHost()` (`@shared/lib/background-work`), not its own `setTimeout`/`setInterval`. A payload is a serializable value with a Zod schema, and a task runs outside the async scope of whoever scheduled it, so one that acts for a user carries who and enters that scope itself. The local manager keeps everything in memory, on purpose: no task tables, outboxes or restart recovery. Read [docs/background-work.md](docs/background-work.md) before adding a Task or a Service
- always use Zod schemas to validate JSON before storing in DB or writing to file, and when parsing JSON read back from DB/file. Define schemas in a dedicated file alongside the service/feature (e.g. `config-schema.ts`) and use `.parse()` at the boundary

- when gating a renderer feature, ask **what it touches, not what the window is** — this computer → `canUseHostFeatures()`, the machine running the API → `!targetIsRemote()`, the window itself → `isElectron()`. `!targetIsRemote()` is *broader* than `isElectron()` (true in every browser), so the two are not one scale of strictness and picking the wrong one silently withdraws the feature from all web deployments. Truth table + full gate inventory: [docs/cloud-workspace.md § Capability gating](docs/cloud-workspace.md#capability-gating-three-questions-not-one-axis)
- gates on where the app runs (OS, desktop vs web, a Store build) ask a **capability** (`src/shared/lib/facts/capabilities.ts`, `src/renderer/lib/capabilities.ts`), never combine facts at the call site. Facts come in two halves: **client** (this window's app and computer, `clientFacts()`) and **server** (the machine running the API, `serverFacts()` in a renderer, `getServerFacts()` on the server); server code reads server facts only, since one server serves many clients. A renderer gets both before its first render with no request: inlined into the web HTML, or from main over IPC. `process.mas` / `process.windowsStore` are read only in `server-facts.ts` (lint). Read [docs/facts.md](docs/facts.md) before adding a fact or a capability

- browser tool text (status line, `Effect:` line, warnings in `agent-container/src/page-status.ts`, `action-settle.ts`, `tools/browser.ts`) states **observations only**: what was seen, or that nothing was and what was looked at. Never infer a negative ("the click was swallowed", "you are at the end") or give advice unless the observation leaves no doubt (Chrome's own error page, a challenge wall). Agents can establish those states themselves with a snapshot or screenshot; a hint only saves them steps, while a wrong hint turns a recoverable run into a failed one. When in doubt, say less
